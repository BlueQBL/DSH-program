# 对谈录 · AI 聊天助手

一个能真正对话的聊天页面：你问，它答，回答**一个字一个字写出来**；一轮轮聊下去它记得你前面说过什么；刷新、关掉再打开，这一页的字都还在；想换话题就点一下清空。

界面不做「聊天气泡」，做的是一份**对谈记录**：页边有序号，一条竖线把一问一答串起来，回答像稿件一样写在正文栏里，正在生成时那里有一道红墨光标在写。

零依赖：Node 原生 HTTP + 原生 HTML/CSS/JS，`npm install` 都不用。

## 运行

```bash
cd ai-chat
node server.mjs          # → http://127.0.0.1:5250
```

启动后终端会告诉你当前是哪种模式：

```
对话模式：本地离线回答（未配置 API Key）
接入真实模型：设置环境变量 DEEPSEEK_API_KEY 后重启（可选 AI_MODEL / AI_BASE_URL）
```

### 接入真实大模型（可选）

不配也能用。配上就是真实模型的回答，其余代码一行都不用改：

```bash
# Windows PowerShell
$env:DEEPSEEK_API_KEY="sk-xxxx"; node server.mjs

# macOS / Linux
DEEPSEEK_API_KEY=sk-xxxx node server.mjs
```

| 环境变量 | 默认值 | 说明 |
| --- | --- | --- |
| `DEEPSEEK_API_KEY` | 空 | 也接受 `OPENAI_API_KEY`。为空即进入离线模式 |
| `AI_MODEL` | `deepseek-v4.1-flash` | 也接受 `OPENAI_MODEL`。服务端的初始默认模型；页面上选过的模型优先 |
| `AI_BASE_URL` | `https://api.deepseek.com/v1` | 任何 OpenAI 兼容接口（也接受 `OPENAI_BASE_URL`） |
| `AI_MODEL_CANDIDATES` | 空 | 逗号分隔，覆盖内置候选模型链（测试用） |
| `AI_STALL_TIMEOUT_MS` | `45000` | 上游多少毫秒没有新内容就算卡住（见下） |
| `AI_FORCE_MOCK` | 空 | 设为 `1` 强制留在离线模式，便于演示 |
| `PORT` / `HOST` | `5250` / `127.0.0.1` | 监听地址 |

### 在页面上换模型

顶部有一个模型选择框，列出你这个上游账号**实际可用**的模型（服务端问上游拿，已过滤掉绘图 / 语音 / 向量 / 视频等非聊天模型 —— 那个账号 156 个模型里滤掉 28 个）。选中的模型存在浏览器本地，刷新后仍然生效。

两条明确的行为约定：

- **默认模型**取 `AI_MODEL`（默认 `deepseek-v4.1-flash`）。你没在页面上选过时就用它。
- **你选过就用你选的，绝不静默替换。** 如果选的模型挂了，会明确报错并让你换一个，而不是偷偷用别的模型回答 —— 那种「界面显示 A、实际回答来自 B」的行为比报错更糟。

### 上游模型挂住时

有些模型会长时间不返回。为了不让你对着「正在生成」干等，服务端用的是**卡住检测**而不是总时长上限：只要还在持续出字就一直等，但**超过 `AI_STALL_TIMEOUT_MS`（默认 45 秒）没有任何新内容就中断**，并提示换一个模型。

实测经验（同一个 Key、同一时刻）：`deepseek-v3.2` 与 `gpt-4o-mini` 稳定在 2 秒左右，而 `deepseek-v4.1-flash` / `deepseek-v4-flash` 会整轮无响应。**这是上游侧的状态，与本项目无关，也可能随时间变化** —— 哪个快就用哪个，随时用 `node test/check-upstream.mjs` 测一遍。

### 上游报错时先跑这个

```bash
node test/check-upstream.mjs      # 或 npm run check:upstream
```

它用与服务端完全相同的配置直接问上游三件事：**这个 Key 能用哪些模型**、**当前模型能不能跑通流式**、**不能的话哪个能用**，并给出可以直接照着改的启动命令。

最容易踩的坑：**第三方代理往往没有你想要的模型名**（例如某个代理在 default 分组下没有 `deepseek-chat`）。此时上游返回 `503 model_not_found` —— 这**不是**「服务暂时不可用」，等多久都不会好。服务端启动时会自动探测可用模型并改用它，启动日志里能看到：

```
  模型 deepseek-chat 不可用：上游没有 「deepseek-chat」 这个模型：…无可用渠道（model_not_found）
  已验证可用模型：deepseek-v3.2
```

想看这个 Key 的全部可用模型（含被过滤的非聊天模型）：`/api/models` 与 `/api/models?all=1`。

## 需求对照

| 需求 | 实现 |
| --- | --- |
| 完整聊天界面，输入问题 AI 回答 | 原生前端，问 / 答按轮次排版，回答支持 Markdown 与代码块 |
| 多轮对话，AI 记得之前说过的 | 每轮把完整历史一并发给模型；离线模式会真的从你的原话里抽取事实并回溯引用 |
| 回答逐字显示（流式输出） | 服务端 SSE 逐段 flush，前端逐帧读取、按帧渲染；实测一条回答产生约 200 个独立数据段，跨越数秒陆续到达 |
| 对话记录保存在本地，刷新不丢 | 主副本在 `localStorage`，流式中的半截文字也实时落盘；服务端在 `data/conversations/` 另留一份兜底副本 |
| 清空对话，方便开始新话题 | 右上角「清空对话」，就地二次确认（不弹模态），清空后本地与服务端兜底副本一起失效 |
| 选择模型 | 顶部下拉框列出本账号可用模型（已滤掉非聊天模型），默认 `deepseek-v4.1-flash`，选择本地持久化 |

额外做了：手动停止生成、出错/中断后重新生成、复制回答、导出 Markdown、跨标签页同步、刷新时自动恢复中断的半截回答。

## 接口

| 接口 | 方法 | 说明 |
| --- | --- | --- |
| `/api/chat` | POST | 主接口。请求 `{ messages, sessionId, model? }`，响应是 SSE 流 |
| `/api/config` | GET | 当前模式（`model` / `mock`）、默认模型、实际使用的模型、接入提示 |
| `/api/models` | GET | 本账号可用的**聊天**模型列表（带 5 分钟缓存）；`?all=1` 含非聊天模型，`?refresh=1` 绕过缓存 |
| `/api/history/:sessionId` | GET | 读兜底副本（会先等本轮落盘任务收尾） |
| `/api/history/:sessionId` | DELETE | 删除兜底副本 |
| `/api/health` | GET | 健康检查 |

`POST /api/chat` 的 `model` 字段就是页面上选的那个模型。它会被校验（只允许字母数字与 `._:/-`），非法值一律忽略并回落到服务端默认 —— 免得被塞进上游请求体。

SSE 帧格式（一行一个 JSON 对象）：

```
data: {"type":"meta","mode":"mock","model":"本地离线回答","sessionId":"s_xxx"}
data: {"type":"delta","text":"**闭包**指的"}
data: {"type":"delta","text":"是函数记住"}
data: {"type":"done","reason":"stop"}
```

中途失败会先发 `{"type":"error","message":"..."}` 再发 `done`，已经写出的部分会保留在界面上，可以原地重新生成。

模型名以 `meta` 帧里的值为初始值；如果服务端换了模型，会在第一段内容之前补发一帧：

```
data: {"type":"model","model":"deepseek-v3.2","switchedFrom":"deepseek-chat"}
```


两个核对脚本，需要服务已在运行：

```bash
node test/verify-sse.mjs     http://127.0.0.1:5250     # 直连 socket 看真实字节
node test/verify-turns.mjs   http://127.0.0.1:5250     # 多轮记忆与兜底副本
```

测试默认自己在随机端口起服务；也可以指向一个已在运行的实例：

```bash
DSH_TEST_BASE=http://127.0.0.1:5250 node test/run-tests.mjs
```

流式测试刻意**不走 fetch**：undici 会把多个响应块合并成一次 `reader.read()`，「逐字」这件事在 fetch 层根本量不出来。所以 `verify-sse.mjs` 和流式断言都用原始 TCP socket，直接数服务端 flush 出了多少个独立数据段、它们之间隔了多久。

## 设计说明

**为什么是「对谈录」而不是气泡。** 气泡是即时通讯的隐喻，追问和回答被压成两条不同颜色的色块，多轮之后就分不清哪句是哪轮。这份界面按**轮次**组织：页边的大号序号是每一轮的锚点，贯穿竖线把一问一答绑在一起，回答用宋体排在正文栏里、按稿件的方式排版。红墨只用在两个地方——「问」标和书写光标——所以「正在写」这件事一眼就能看见。

**流式渲染的取舍。** SSE 到达的节奏不可控，逐 token 改 DOM 会让长回答抖动。前端用 `requestAnimationFrame` 合并成「一帧一渲染」，并且流式期间只重画当前那一条，不重建整个列表（否则滚动锚点和光标位置都会跳）。

**落盘节流。** 每来一个 token 就 `JSON.stringify` 整段对话，一轮回答就是上百次全量序列化，对话越长越卡。改成以「一个流式周期」计时：每条回答的**第一个**增量立即落盘（这样中途刷新一定看得到正文），之后最多每 250ms 一次，`finish` 和页面 `pagehide` 时立刻补写。

**离线模式不做假。** 没有 API Key 时，离线回答会如实说明自己不是真实模型，同时真的从你的原话里抽取事实（称呼、职业、在学什么、在做哪个项目）并在你追问时回到上文原样引用。演示的是机制——多轮上下文、逐字输出、刷新不丢——而不是伪装成模型推理。

## 已知限制

- **单会话**：只有当前这一轮对话，没有历史会话列表。清空即开始新话题。
- **离线回答没有知识**：只有少量技术小抄模板，其余问题会明确说「不编造」。
- **`localStorage` 约 5MB**：超长对话会写满，此时界面仍可用，只是不再落盘（会在控制台给出警告）。
- **硬杀进程可能丢最后约 250ms 内容**：节流窗口内的最后一次写入靠 `pagehide` 补，正常刷新和关闭页面都没问题。
- 服务端兜底副本**不做鉴权**：它只按 `sessionId` 存文件，适合本机单人使用。放到公网前需要自行加访问控制。
- **服务端不能常驻**：`node server.mjs` 需要一个保持打开的终端窗口。

## 开发过程中修掉的几个真问题

留在这里，因为它们都是「不报错但功能不对」的类型：

1. **一个字都发不出去**：`res.on('close')` 在请求体读完时就会触发，导致 `aborted` 一开始就是 `true`，生成循环第一次迭代就 `break`。改为只认「请求被中止」和「响应未写完却被销毁」。
2. **离线回答整段丢失**：离线生成器 yield 的是裸字符串，消费端按 `piece.text` 取值得到 `undefined`，每次都被 `if (!piece.text) continue` 静默跳过，界面上只剩空回复。现在统一契约为 `{ text }` / `{ error }`，并在循环里显式校验。
3. **「学习」抽出 `习`**：中文里「学习」=「学」+「习」，动词写成 `(?:学习|学)` 交替时，`学习` 失败后引擎会退一步只匹配 `学`，把「习」当成学的内容。改为按动词切分字符串、再从右取名词片段，不做回溯。
4. **流式期间一个字的正文都没落盘**：落盘节流以「谁最后写盘就重置计时」实现，`pushAssistant` 之后整段回答在写完前都不会落盘，中途刷新只能看到提问和空回复。改为以「一个流式周期」计时。
5. **`done` 早于兜底副本落盘**：客户端收到结束信号后立刻读历史会读到空。服务端登记未完成的落盘任务，读历史时先等它收尾。
6. **重新生成会重复一条提问**：改为复用原提问，摘掉旧回答后重新回答，保持一问一答的结构。
7. **把「模型不存在」报成「服务暂时不可用」**：上游在 `model_not_found` 时返回的是 503，旧代码只看状态码，于是让用户去等一个永远不会好的东西。现在按上游错误码细分，区分「能重试」与「要改配置」，并把上游原始说明、模型名、可用的替代模型名一起给出来。
8. **默认模型名在第三方代理上往往不存在**：启动时先探测一次，自动改用真正可用的模型 —— 否则第一个提问的人要多等十几秒去撞墙。
